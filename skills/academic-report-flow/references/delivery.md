# Delivery - Decision 3 (review of each version) and publication

Phases `review` (human gate) and `deliver`. Generation never publishes: the build ends at the validated PDF under `outputs/<materia-slug>/`, writing nothing into `~/Documents`.

## Review (`next: review`, artifact `reports/<wf>/final-review.yml`)

Present the exact PDF of the current version (v1 first, then v2, v3...), opened in full, never a summary, together with the rubric status and the list of open findings (`RUBRIC FINDINGS`, `missing` and `partial` requirements, a failing validation receipt): v1 is a complete formatted artifact, not a claim that the rubric is met. The user answers with edit orders or new evidence, which produce the next version (`approval.md`, Versions), or with an explicit OK. With a `rubric.yml`, run `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/rubric_grade.py" <folder>` first and present `rubric-grade.md` unchanged beside the PDF. It has two parts, guide coverage and the leveled grade, and never calls coverage a grade. Guide coverage, over the criteria that are not `origin: teacher` (a legacy plan is all coverage): per criterion the weight, evidence location (section and PDF page), covered points and gap, then the total over the rubric total and as a share in %. Only the tool computes it, from the verifier's matrix (`weight x found/total`, `partial` counts 0.5, a red check zeroes the criterion, equal weights when the rubric has none); label it a mechanical estimate, not the teacher's grade: it says what the body covers, never how well. Teacher rubric (leveled): the level the independent strict grader recorded in `leveled-grade.yml` (`production.md`) per teacher criterion, points over the top level and what is missing for the top level, then the leveled grade (weighted total) and its /10 equivalent; it is orientative, not the teacher's grade either. Relay every `warning:` line (no or stale `leveled-grade.yml`, an unknown id or points, a criterion at half the top level or less) and every `note:` (one below the top level) to the user; they inform the next edit orders. It is written to the work folder, never the delivery folder, and never blocks the review or delivery; re-run it when the PDF changes. When `report.yml` sets `deliver_bibliography: true`, present the declared `.bib` alongside the PDF: the human OK covers both artifacts or neither. Only an explicit OK of that exact set produces the marker, binding `pdf_sha256` (plus `bibliography_sha256` when declared, computed from the `.bib` bytes only after that explicit OK), `reviewed_at`, `reviewed_by`. A review is never granted automatically; silence is never a yes and the marker is never inferred; a decline or any other answer writes nothing and review stays `pending`. Record the gate with the writer, never with `printf`: `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/final_review_marker.py" record <folder> --by "<name>"` reads the PDF (and declared `.bib`) from `report.yml` and writes `final-review.yml` plus the snapshot `reviewed-body.md` (the reviewed `body.md` bytes, bound through `body_sha256`) together, atomically.

A changed declared `.bib` stales the marker and returns the route to `review`. A rebuilt PDF does the same, unless the edit since the review was bounded: at most 40 changed words (inserted plus deleted) between `reviewed-body.md` and the current `body.md`, no Markdown heading added, removed or edited, `validation.yml` passes for the CURRENT PDF (and bibliography), and the `report.yml` render settings still equal the `render_sha256` recorded at review time (delivery-only keys excepted; a PDF that changed because of render settings was never reviewed). Then `final_review_state` returns `carried`, `doc_status` reports review `done` with "bounded edit since final review (N words)", and the publisher accepts it like `current`: the human question is skipped, nothing else is. Verify, rebuild and validation still run after every edit, and a missing or altered snapshot, a validation for another PDF or a hand-written marker without `body_sha256` or `render_sha256` is never trusted. Delivery runs only after this gate is `done` in the flow (`deliver_report.py` itself only warns on a missing or stale review, see Deliver); never refresh a stale marker without a fresh explicit OK.

PDF handoff: open the PDF for the user with the exact `pdf_viewer.py` command from `doc_status` guidance before asking for the OK; it launches `$REPORT_PDF_VIEWER`, else brave (it follows internal links; zathura does not), else `xdg-open`, detached. Also give its clickable `file://` link. If the viewer cannot start, say so and give the link; never send screenshots, the user reviews the PDF itself.

## Deliver (`next: deliver`)

Artifact: `~/Documents/<category>/[<subject-slug>/]<slug>/<slug>-vNNN.pdf` (plus the same-version `<slug>-vNNN.bib` only when `deliver_bibliography: true`). Never copy or version by hand:

```bash
"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/deliver_report.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/"
```

Publish only on the user's explicit instruction to publish, given after the review; `doc_status` waits for it. `tools/deliver_report.py` is the only publication route. It checks for a `validation.yml` receipt with `result: pass` for the exact PDF bytes and a valid `final-review.yml` (`current`: its `pdf_sha256` matches those bytes; or `carried` across a bounded edit, see Review). These checks warn, never block: a missing, failed or stale receipt (or its `bibliography_sha256`), an absent or stale final review, a stale `build/generation.yml` next to a valid `approval.yml`, and for a report built as v1 (no `approval.yml`, with a current `build/generation.yml`) an unmapped guide inventory, a `content-check.yml` that does not pass (an unresolved rubric failure without an accepted gap, an unresolved citation) and, when either gate is `carried`, a PDF whose body record (`<pdf stem>.body.sha256`) does not hold the sha256 of the current `body.md`, each print `warning: <message>` on stderr and the PDF is still delivered with `PDF ENTREGADO CON ADVERTENCIAS`; a warned receipt grants none of its gates. Relay every warning to the user. Delivery refuses (exit 1, nothing created) only when there is nothing to deliver or nothing readable: a missing PDF or declared `.bib`, an invalid `report.yml`, an unparseable `validation.yml`, a malformed `final-review.yml`, a missing publication identity, a version-claim error, a report with neither `approval.yml` nor `build/generation.yml` (nothing vouches for the PDF), or a report without `approval.yml` whose `build/generation.yml` is not current for the PDF (without approval the generated identity is the integrity anchor, so it refuses with `Falta o está obsoleta la identidad del PDF generado`). A warning never says that nothing is published: a delivered PDF's warnings end with `el PDF se entrega igual`. `approval.yml` is the exception that is not a quality check: a report with `approval.yml` keeps the `approval.yml` path (`APPROVAL_CURRENT`), and a present but stale or malformed `approval.yml` always refuses, whatever `build/generation.yml` holds, because it is the user's explicit approve, a human decision like the questions to the user. Rebuild and validate after a bounded edit before delivering. The hash before validation must match the hash immediately before publication. Publish only the confirmed PDF output.

- Destination: no `delivery_pdf:` or user-selected path: `~/Documents/<automatic-category>/<slug>/<slug>-vNNN.pdf`, category from the confirmed route (`Academicos`, `Proyectos`, `Profesionales`, `Tecnicos`, `Otros`), `<slug>` the stable ASCII slug of the confirmed title.
- Academic route: the confirmed subject scopes one level deeper, `~/Documents/Academicos/<subject-slug>/<slug>/`: the canonical alias when the shared `output_router` vocabulary knows it, otherwise the subject's own stable ASCII slug, so a newly named course gets its own folder; only a missing subject has no level (academic validation refuses it before delivery), and the tools never invent a fallback bucket. Non-academic routes are unchanged.
- Delivery folder override: `delivery_dir:` in `report.yml` (non-empty string; `~` expanded, a relative path resolved against the report folder) replaces the whole `~/Documents/...` layout, so a course can receive its PDFs in its own repo folder such as `<course-repo>/unidad-1/ape-1/documento/`. The same `<slug>-vNNN.pdf` register, hashing and locking apply inside that folder; any non-string or empty value is a configuration error. Without the key nothing changes.
- Versioning: first unique artifact is `v001`; a matching SHA-256 reuses that version; changed content atomically claims the next monotonic version without overwriting a concurrent publisher, then verifies hash equality. Done = a published `<slug>-vNNN.pdf` hashes equal to the final PDF; delivery has no failure state (absent or non-matching is `pending`).
- Declared bibliography (opt-in): only `deliver_bibliography: true` ships the `.bib` the report already selects (`bibliography:`/`bib:`, default `sources.bib`); a `sources.bib` for citations never travels merely because it exists. It must be a regular non-empty `.bib` inside the work folder that parses (traversal, absolute paths and symlink escapes refuse). `validation.yml` and `final-review.yml` must both record its `bibliography_sha256`. The pair ships as `<slug>-vNNN.pdf` plus `<slug>-vNNN.bib`; reuse compares the complete set, so the same PDF with a changed `.bib` claims a new version, a partial pair is never a delivery, and a failed claim cleans only its own files.
- Delivery folders are PDFs only (plus the declared versioned `.bib` and the course template's `README.md`, which is left untouched): never a manifest, `report.yml`, `body.md`, `sources.bib` (undeclared), spec, figure, audit, contact sheet, log, receipt or intermediate.
- Git: a course folder (`~/Documents/Academicos/<subject-slug>/`) may be the user's repository. Do not run any Git command (`git init`, `git add`, `git commit`, `git push`) in the delivery tree; the user owns every Git operation, Git metadata stays at the course root, and each per-document folder stays PDFs-only. Do not write any file other than the versioned PDF (and the declared `.bib` pair).
- Never create, repair or refresh `approval.yml` or `final-review.yml` to make publication pass. Publication is not approval and grants no `VISUAL_PASS`, `HUMAN_REVIEW` or `READY_TO_SUBMIT`; do not report a run as `READY_TO_SUBMIT` from publication alone. Report the published path and version, say the receipts are unchanged, re-run `doc_status` (all `done` reports `next: done`).
- After the teacher returns the grade: record it in the course feedback log with `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/course_memory.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/" --add-delivery --date <YYYY-MM-DD> --grade <points> --max <scale> --comment "<teacher comment, verbatim>"` (one `--comment` per comment; `--work` defaults to the work folder name). It appends one entry to `academic-sources/<course-slug>/feedback.yml` and leaves earlier deliveries as they are; the next report's plan reads it. Add `--predicted <x>` with the leveled grade /10 the report had at delivery (`rubric-grade.md`): the read then prints the mean absolute difference between predicted and teacher grades with its n, an orientative calibration of the strict grader (Redes U1: teacher 6.0, 9.0, 6.0, 5.0, 8.5 against predicted 7.0, 7.5, 7.5, 6.0, 7.5 gives 1.2 with n=5), never a gate. Bad input or a malformed log is a `warning:` and nothing is written; it never blocks.
