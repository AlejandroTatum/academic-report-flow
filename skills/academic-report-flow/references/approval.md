# Approval - Decision 2 (draft approval + format batch)

Phases `approval` (human gate) and `format`. No executor is delegated to the gate: the orchestrator presents the prompt and only the human's explicit answer may produce the marker. `doc_status` offers it only once the body check passes (`content.md`) and the verify passes (`production.md`): verify runs before approval, so the human approves with the requirement matrix in hand.

## Marker

Artifact `reports/<wf>/approval.yml`, binding the exact bytes of `body.md` to a named human decision:

    schema: academic.doc-approval/v1
    body_sha256: <64 lowercase hex of the exact body.md bytes>
    approved_at: <ISO-8601 UTC>
    approved_by: <non-empty human identity>

Record the gate with the writer, never with `printf`: `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/approval_marker.py" approve <folder> --by "<name>"` writes `approval.yml` and the snapshot `approved-body.md` (the exact approved bytes) together, atomically, from the current `body.md`. The snapshot is what lets a bounded edit keep the approval (see "Review loop").

Silence, an inferred yes, a restated plan, or an agent decision never produces `approval.yml`; a decline writes nothing. Done = marker exists and `body_sha256` matches the current `body.md`, or the approval is carried across a bounded edit (below); absent or stale is `pending`, malformed is `blocked` (`approval_marker_malformed`). Never create, repair or refresh a marker except from a fresh explicit approval. Approval grants no build or delivery.

The gate prompt is lossless and blocking: complete decision, consequences and exact allowed answers, no silent default. The approver reads `body.md` in full: point to the complete body, never a summary, and say that generation happens only after this approval.

## Preview before asking

Before asking, build a preview with `build_report_auto.py <folder> --no-approval-check` (it records the sha256 of the `body.md` it rendered next to the PDF; `doc_status` keeps the gate closed with "rebuild the draft PDF" while that record is missing or differs from the current `body.md`), audit it with `visual_pdf_auditor.py <preview pdf>` and inspect it against the blocking-defect list in `production.md`: every page on the first preview, then only the Changed pages its `visual_qa.md` lists (a pixel-identical page keeps its verdict). Fix layout defects in `body.md` first (re-run the body check), then rebuild. The message immediately before the approval `ask_user_choice` is the approval packet printed by `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/approval_packet.py" <folder> --open`, pasted unchanged (`--open` also opens the fresh preview PDF in the reviewer's viewer so the user can review without hunting for the file; it never opens a stale or missing preview): clickable Markdown links with absolute `file://` URLs to the preview PDF, `body.md` and the latest DOCX draft, plus the verify result, one summary row per criterion (cumple/falta, found/total), the missing items, the deletion candidates and the findings; the per-requirement evidence matrix is for agents and stays linked in `content-check.yml`, never pasted. It flags a stale preview or verification; never present the gate without them, and never with either stale. The preview is never the final artifact: it predates `approval.yml`, so generate stays `pending` and the final build runs after approval.

## One batch: approval plus format

Ask in ONE batch, the same batch for approval and format, through `ask_user_choice` with suggested options, no free text: (1) approve `body.md` (exact bytes); (2) document format APE, AA, ACD or libre (`format_hint:` first when present), delivery format PDF or DOCX (`output:`), `format_spec` when `libre` is chosen (suggested options such as "documento sobrio sin portada" or "con portada"), and the metadata the chosen format still requires (subject, teacher, APE or ACD identification fields, group members). When the subject has a course repo (`~/Documents/Academicos/<subject-slug>/AGENTS.md`), the same batch confirms the delivery folder `unidad-<unit>/<practice_type>-<practice_number>-<topic>/` (the type is the course's own word, from `course_profile.py --check`) (suggest `metadata.unit`, `metadata.practice_number` and a short `metadata.topic` such as `actores-sdd`, read from the guide; `tema` is an alias of the title, never the topic). Never infer an answer and offer no default. Record each format answer in `report.yml` as soon as it is given, even when the user requests changes, then run `tools/course_profile.py <folder>` so `delivery_dir:` is set before the final build. Only `approval.yml` waits for an explicit approve; a decline or edit order writes no marker. Approval binds only `body.md` bytes; the format answers are plain `report.yml` data, so a request for changes reopens only the body approval: the next gate asks "approve `body.md`?" plus only the format fields `report.yml` still lacks (`doc_status` names them), never what it already records. The user approves once: the final build, validation and delivery then run without asking again, and later `delivery_dir`/`deliver_bibliography` edits do not stale the built PDF.

## Review loop - literal edit orders

The user answers with literal edit orders ("in paragraph X replace '...' with '...'", "delete section Y", "move this paragraph before that one"). Apply the user's text verbatim: never polish, rephrase or improve user-authored text; polishing forges authorship. Batch all literal edit orders from one reading into one round: apply them all verbatim, rebuild the preview PDF, and only then ask for re-approval with the same links, unless the round stayed bounded (below). A bounded edit keeps the approval and asks nothing: the tool decides deterministically from a word-level diff between `approved-body.md` and the current `body.md`. An edit is bounded when at most 40 words change (inserted plus deleted) and no Markdown heading line is added, removed or edited. `doc_status` then reports approval `done` with "bounded edit since approval (N words)" and `approval_state` returns `carried`, which every gate (`doc_status`, `build_report_auto.py`, the publisher) accepts like `current`. The snapshot must hash to `body_sha256`; a missing or altered snapshot is never trusted. Any other edit (more than 40 words, or any heading touched) makes the approval stale: the route returns to `approval` as `pending`; present the gate again for the new bytes and record it again with the writer.

A carried approval skips only the human question. Verify, the body check, the rebuild and validation still run after every edit: re-verify with `--since verification.yml` (`production.md` step 5: only the criteria whose section changed go to the verifier), rebuild the preview, and re-inspect only the Changed preview pages. Each edit round re-checks only what changed, never the whole document. Generate and validate run once, after the final approval. The loop repeats until the user explicitly approves, or until the edits stay bounded.

## Format (phase `format`, artifact `reports/<wf>/report.yml`)

Normally `done` without a stop because the batch already answered it. It is a completeness check plus fallback: when `report.yml` lacks a known `format:`, `output:` or that format's required metadata, ask only the missing fields `doc_status` names and never re-ask what `report.yml` records.

- One question for format selection through `ask_user_choice`: APE, AA, ACD or libre (hint first; the hint is not a choice, wait for the answer before recording `format:`). Metadata gaps are separate `ask_user_choice` prompts, never free text and never a second format-selection question.
- Delivery format PDF or DOCX is asked in the same format step, has no default, and is never inferred from the request or material; record it as `output:`.
- Delivery folder: with a course repo and no `delivery_dir:`, `doc_status` keeps format `pending` until the final build (a draft preview does not count); record `metadata.unit`, `metadata.practice_number` and `metadata.topic`, then run `tools/course_profile.py <folder>`. A delivery folder that holds anything besides `<slug>-vNNN.pdf` and its paired `.bib` keeps format `pending` with "delivery folder unusable" and the publisher's reason: ask the user to empty it or pick another `delivery_dir` now, before the build and the reviews, never after the final OK.
- `ape`: practical-experimental technical report. Fixed sections: Objetivo(s), Materiales, Procedimiento (steps as a list), Resultados, Preguntas de Control, Conclusiones (tied to the objective), Recomendaciones, Bibliografía/Referencias (IEEE, or APA with `citation_style: apa`), Anexos. When the teacher says to leave a fixed section out, record its exact title under `ape_omit_sections:` and drop it from the body and the rubric; any other title is rejected. Extract its identification fields (cycle, unit, learning outcome, practice number and type, schedule, place, planned time) from the teacher's guide; the user only confirms or fills gaps. When `practice_type` is Grupal, record `metadata.members`.
- `aa`: academic activity report, rendered with `aa-report.tex` (editorial design; only page 1 is creative, with the letterhead, the left-margin identification ficha and the large serif title; pages 2+ are full width). Metadata: title, subject, teacher, student, date. Fixed sections, in order: Objetivo(s), Introducción, Desarrollo (free subsections), Conclusiones, Referencias (printed by the template; an authored heading is optional but must follow Conclusiones), Anexos (optional), Declaración de uso de IA (optional). `template: unl` keeps the old UNL look.
- `acd`: in-class session record (ACD), rendered with `acd-report.tex`. Its identification block reuses the APE keys: `title` is the session topic, `date` the session date and `practice_number` the ACD number, plus subject, teacher, student, cycle, unit, learning outcome, schedule, place and planned time; extract them from the teacher's guide like APE. Fixed sections, in order: Objetivo(s), Síntesis de contenidos abordados, Actividades desarrolladas en clase, Análisis / reflexión, Conclusiones, Referencias (printed by the template, as in AA), Anexos (optional). Markdown definition lists render as the label column of the record sheet.
- `ape`, `aa` and `acd` have no cover by default; an explicit `cover:` in `report.yml` still wins. Their section lists are checked at draft time (`content_check`: `ape_structure`, `aa_structure`, `acd_structure`) and again by final validation, so a draft missing a fixed section cannot be approved.
- `libre`: wait for the user's own specification and record it verbatim as `format_spec:`; the plain template applies by default.
- Every format cites with IEEE by default; `citation_style: apa` is the opt-in when the guide demands APA, on any route; `ape`, `aa` and `acd` map to the academic route, `libre` to the plain template. Missing metadata keeps the phase `pending`; an unrecognised value is `blocked`, never a silent fallback. Never fill identification fields on the user's behalf.
