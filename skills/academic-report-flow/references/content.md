# Content - sources, plan, draft

Stages `research`, `plan`, `draft`; one artifact each. After each: re-run `doc_status`, report the new phase. No stage writes another stage's artifact, `approval.yml` or `validation.yml`.

## Research (executor `research-workflow`, artifact `reports/<wf>/sources.bib`)

Research is mandatory: at least 5 (or the report's `min_sources:`) eligible entries in the document's own BibTeX file (or the `bibliography:`/`bib:` path in `report.yml`): `book`, `inbook`, `incollection`, `article`, `inproceedings`, `conference`, `phdthesis`, `mastersthesis`, `techreport`. Web-only `@misc`/`@online` never count; `doc_status` keeps the phase `pending` until the file holds them. `min_sources: N` (top-level positive integer, invalid values rejected) replaces the minimum only when a requirement limits sources; `min_sources: 0` (no bibliography, nothing to cite or verify, no references section) is accepted only on a non-academic route, and the academic route always needs at least 1. `uncited_bibliography: true` (academic route only, mutually exclusive with `min_sources`) is the explicit opt-in for a course that forbids in-text citations: the research gate then needs at least 1 entry of any type (e.g. a single `@misc` for class slides), no citation is required, and every entry in the bib is printed (`\nocite{*}`), so the bib must be exactly the list to print.

- Every entry is real and verifiable (author, title, year, publisher/venue): never invent a source, locator, quotation, date, author or finding. Citations default to IEEE (biblatex `style=ieee`); `citation_style: apa` (default `ieee`) in report.yml is the opt-in, used only when the course guide demands APA (author-year `(Author, year)`, PDF only; the DOCX builder rejects it).
- Protocol: `research-workflow` (`references/research-protocol.md`). Its `research/evidence-matrix.md` (and `evidence.yml`) is pre-document evidence: it never satisfies the phase or chooses type, structure, style or prose.
- Local inspected sources feed the bibliography: `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/source_library.py" pack --only-inspected <query>` over `$REPORT_CONTENT_ROOT/academic-sources/manifest.yml`. Only `inspected: true` entries are eligible; an uninspected source stays a `lead`, never in `sources.bib`.
- After writing `sources.bib`, run `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/verify_sources.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/"`. A DOI is checked in Crossref, then DataCite (arXiv, Zenodo); a web-only `@misc`/`@online` entry with a `url` (or `\url{}` in `howpublished`) and no DOI or ISBN is VERIFIED_URL when the page answers, which proves the page exists and never counts toward the source minimum. Finish only when every entry is VERIFIED, VERIFIED_WITH_WARNINGS or VERIFIED_URL; fix or replace MISMATCH and NOT_FOUND, give NO_IDENTIFIER entries a DOI, ISBN or (web-only) URL, move a MALFORMED_FIELD address containing `%` from `howpublished = {\url{...}}` to the `url` field, and verify again.

## Plan (artifact `reports/<wf>/rubric.yml`, schema `academic.rubric/v1`)

A confirmed teacher template is mirrored too: its sections, order and formatting. The plan mirrors the teacher's rubric: one criterion per rubric item (`id`, `title`, optional `weight`), each mapped to the body section that satisfies it. A rubric item no section can satisfy is a gap to raise with the user, never a criterion to drop, merge or invent.

- Two lists, never one: the guide says what to do, the teacher's rubric says what is scored, and a report can cover every guide step and still score low. Mark each criterion `origin: guide` (a demand of the guide) or `origin: teacher` (a row of the grading rubric). A teacher criterion carries the rubric's real `weight` and its `levels:` copied verbatim, one `- points: <n>` plus `descriptor: <the level's text>` per level; never paraphrase a descriptor and never fold a teacher row into a guide criterion.
- No teacher rubric: say so to the user before planning and ask for it once. Only when the user confirms there is none, record top-level `teacher_rubric: none`; criteria then come only from the guide's explicit demands (sections, questions, deliverables it states); never from the agent's idea of a good report. With neither rubric nor explicit demands, ask the user instead of inventing criteria. `doc_status` reports a plan without teacher criteria as `warning: guide-only plan, no teacher rubric`: relay that warning to the user every time it shows; it never blocks.
- `format_hint: ape`: map criteria and checks to the fixed APE sections (Objetivo(s), Materiales, Procedimiento, Resultados, Preguntas de Control, Conclusiones, Recomendaciones, Bibliografía/Referencias, Anexos); the hint guides planning, never chooses the format. The guide, rubric and explicit user instructions govern content; route and format section lists are structural defaults, not demands to invent extra content. Resolve a genuine conflict with the user; record applicable omissions rather than fabricate.
- Write deterministic `checks:` before the draft exists for every mechanically checkable criterion (rubric TDD: red now, the draft turns them green). Types: `heading_present`, `contains`, `matches`, `verbatim_from_guide`, `ordered_list`, `min_citations`, `figure_referenced`, `link_present`, `keywords_from_section`. Checks are document-wide by default: use `section:` only when the property must live in that section (a heading restructure breaks scoped checks). Purely semantic criteria may have none. A `contains` or `verbatim_from_guide` text runs on `body.md`, `body.typeset.md` and the PDF text, so it must read the same in all three: `rubric_plan.py` rejects a text with a formula (`$...$`, `\ln`, `x^2`), a Unicode superscript or subscript (`m/s²`, `x₁`) or a figure path (`.png`, `![...](...)`). Check the words around a formula, or write a `matches` pattern that accepts every notation (`2(³²|\^\{32\})`), since a pattern never runs on the PDF text; use `figure_referenced` for figures.
- Deliverables become checks: list every deliverable the guide states for a criterion under `deliverables:` (one entry each, e.g. "Wokwi link for Part A", "Table of results"), and write one non-heading check per deliverable (`link_present` for each link, `contains`/`matches` for each table or answer); a heading only proves the section exists, and `rubric_plan.py` rejects a criterion with fewer non-heading checks than deliverables.
- Guide inventory: run `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/guide_facts.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/" --inventory` (needs `guide:` in `report.yml`). It numbers `G1`, `G2`... the guide sentences that read as a demand: `mandate` (a verb such as Elabore, Compare, Justifique, or "debe"), `question` (¿...?) and `deliverable` (entregable, adjuntar, enlace, captura). It is a heuristic: it over-detects and misses, so it never replaces reading the guide. Name every item in some criterion's `deliverables:` (with its check) or `covers:` (list of ids or exact texts, for a semantic item that has no check), or list it under top-level `not_applicable:` as `- item: G4` plus `reason: <why>`; use `not_applicable:` only for a line that is not a demand, never for one you skipped. `rubric_plan.py` exits 1 with `guide_inventory_unmapped` listing unmapped items; `doc_status` shows them as a finding and the publisher refuses while any stays unmapped; it checks coverage, never quality or a score. Without a guide there is no inventory.
- Demands only a person can close (an ADR versioned in the repo, a signature, a submission the text can only plan): list them under top-level `needs_person:` as `- item: G26` plus `reason: <what the person must do>`, the same shape as `not_applicable:`; an item cannot be in both lists, and it still needs its criterion. The verify brief tells the verifier to report each as `partial` with that reason as `gap` when the text only states the plan, without a finding; the `--verification` output and the `doc_status` verify detail show it as `waiting for a person: <requirement> (gap: <reason>)`, apart from fixable findings. Nothing else changes: the criterion stays `falta`, the check `fail`, and publication is refused until the person accepts the gap (`production.md` step 6).
- Set a word ceiling, never a minimum: top-level `max_words:` (positive integer) sized to what the guide asks; a criterion may set its own `max_words:`, otherwise it gets its weight share of the total when every criterion has a `weight`. Only prose counts (tables, including a plain-text `Tabla N.` caption and its `- a; b` data lines, code, math, images and citation keys are excluded).
- Run `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/rubric_plan.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/"`; it blocks on a malformed rubric (`rubric_malformed`).
- Then run `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/rubric_trace.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/"`: without a body every criterion is uncovered (exit 1), the board the draft turns green. It is read-only and lists weight (equal weights when the rubric has none), covering sections, checks and requirements per criterion.
- The rubric is frozen once the draft starts: fix the draft, not the rubric, to turn a check green or close a finding; change `rubric.yml` after that only on the user's instruction. Any change stales the verification (`doc_status` verify says `rubric.yml changed since the check`); one that only touches `max_words` values keeps the `--since` carry (`production.md`, Verify).

Verification states (`verification.yml`, `content-check.yml`): each requirement is `found|partial|missing`. `partial` means covered in part: quote what is there as `evidence` and write what is still absent as `gap`; both are required, and a quote absent from `body.md` downgrades it to `missing`. It never scores: the criterion stays `falta` until every requirement is `found`, the gap shows in the v1 findings, `rubric_trace.py` and `rubric-grade.md`, and only `rubric_grade.py` weighs it (0.5). Files without `partial` or `gap` load unchanged. A `missing` or `partial` requirement is a finding: v1 is still generated and the publisher refuses it. A `partial` the user explicitly accepts with their name and a reason (`production.md` step 6, `accepted_gaps.py`) stops blocking publication; the criterion still reads `falta` and the grade still weighs it at 0.5. Never accept a partial on your own: try to close it through the user's edit orders first.

## Draft (artifact `reports/<wf>/body.md`)

The draft phase produces exactly one artifact: the full body that becomes v1, from `rubric.yml` and the researched sources, in the document's language. Cover every rubric criterion in the section the plan mapped, with proposed figures where they genuinely help (built with `academic-visual-builder`, named on their own line as `Figura: <caption> (<relative/path.png>)`; table and figure rules: `visual-directions.md`, Tables and figures). Cite with `[@key]` resolved against `sources.bib`; every claim traces to an entry there.

- Plain text only: the draft is the content, never backend formatting. The only markers are `# `/`## ` section titles and `[@key]` citations; fenced code listings are content and stay. Formulas go in readable plain notation (`e = |x1 − x0| / |x1| · 100 %`, Unicode sub/superscripts allowed), data as plain sentences or lines, links as bare `https://...` URLs. Never write math (`$...$`), LaTeX commands, pipe tables, `![...](...)`, bold or `<!-- -->` directives here (currency such as `$5 y $10` and Windows paths such as `C:\Users\...` are plain text): formatting is applied in `body.typeset.md` before v1 (`production.md`, Typeset), so a formatting fix never invalidates verified content.

- Style: human and natural, neither overly technical nor flattering or obsequious: direct academic prose with technical precision that explains the actual work done (what was built, measured, compared or decided) rather than narrating rubric compliance. Use concrete referents: name the exact document or result instead of a vague label such as "companion document". Model the tone on how the user writes (their messages in the session). No stock AI phrasing, no padding. The draft is a starting point for the user's review of v1, offered for literal edit orders, not admiration.
- Concision (quality over quantity; no guide asks for more text, so there is never a minimum length):
  - Skeleton from the guide: every section and paragraph answers a guide or rubric requirement; a paragraph that answers none is deleted. Each paragraph adds new information: cut repetition, circular wording and filler. No generic introductions, "importance of the topic" openers or closing summaries.
  - Answer first where appropriate; 2-3 supporting sentences are a guideline, not a limit on necessary explanation.
  - Data, specs, mappings and formulas go on their own lines (one item or equation per line), never packed into prose; typeset turns them into tables and display equations.
  - Include theory needed for the requested coverage and audience; avoid unnecessary basic definitions.
  - Respect the plan's word budget (`max_words`); it is a ceiling, never a target. Keep explicit word limits of the assignment (guide, rubric or user), including a minimum when one is stated; never invent a word quota the assignment does not state.
  - Fix redundancy by cutting or restructuring; add necessary evidence, context or explanation to correct an incomplete answer. Never invent facts or remove required coverage; follow the authorship policy in `approval.md`.
- Body structure: sections start at `# ` (a body using only `##`/`###` numbers them 0.1.); `##` only for subsections under a `#`. The format's fixed headings (APE, AA, ACD) are checked in typeset, not here.
- Presentation defaults (numbering, cover, template) come from `report.yml`, never from the draft.
- After each section, run `rubric_trace.py <folder> --section "<heading>"` (same command as in Plan): the criteria that section serves must be covered before the next section. Exit 2 means no criterion maps to that heading (a deletion candidate).
- Body check before verify: run `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/content_check.py" "$REPORT_CONTENT_ROOT/reports/<work-folder>/" --body-check`. It runs the mechanical part (level-1 headings, `plain_text`: no backend formatting outside code, citations resolve, the rubric checks, eligible sources cited, the word budget, no stock filler phrases, paragraphs over 80 words as advisory warnings, `prose_findings` lint, a formulaic opener in the conclusions section), exits 1 on any FAIL and writes nothing. `doc_status` runs the same check and keeps `next: draft` on every failure except two content findings, `rubric_checks` (a rubric check still red) and `eligible_sources_cited`: it lists those as findings, they never stop v1, and each stays a publication condition (`content-check.yml` must pass, `delivery.md`). Fix the other failures in the draft and close findings where the evidence allows; never claim a red check as met. The draft never writes verification.yml.
- Prose lint (`prose_findings`, `concision.py`): each entry is `{location, kind: repeticion|circular|ambiguo|relleno|registro, quote, fix, pattern}`, at most 20, advisory except the first pattern. Patterns: `formulaic_conclusion` (FAIL: a sentence in the conclusions section opening with `Se concluye`, `En conclusión`, `Para concluir`...), `empty_opener` (`Como es sabido...`), `wordy_phrase` (`en base a`, `subir arriba`...), `stacked_connector` (`Por lo tanto, en consecuencia`), `repeated_start` (3 consecutive sentences or paragraphs starting with the same two words), `repeated_ngram` (7+ words repeated in a later paragraph), `long_sentence` (over 35 words). Rewrite each flagged quote by cutting or restructuring; leave repeated technical terms and a deliberate enumeration. The tool lints `body.md` in `--body-check` (warning) and records the findings in `content-check.yml` under `prose_findings` (older markers lack the key and stay valid), together with the verifier's own entries whose `quote` is verbatim in `body.md` (the others are dropped and listed in `findings`). They never change the verdict.
- Editorial pass before v1 (not an approval gate, no human stop): once the verifier answers, reread the whole body and apply this pass together with its corrections in the same edit round, before `typeset`; write to the same rules from the first draft. It adds only what the prose lint, the verifier's semantic findings and the word budget do not check:
  - Concrete referents: name the exact document, component or result instead of a vague label such as "the companion document", "this element" or "the results above".
  - Each paragraph adds new information around one central idea; cut what only restates an earlier paragraph, keeping every necessary explanation and every piece of evidence.
  - The prose explains the actual work rather than narrating rubric compliance ("this section meets criterion 2").
  - Tables and figures against `visual-directions.md`, Tables and figures.
  It sets no score or quota. An edit beyond the bounded-edit limit re-verifies with `--since` (`production.md`, Verify).
- Done = `body.md` has non-whitespace content (unreadable is `blocked`). The draft never writes `approval.yml`, never builds, hashes or publishes. Corrections follow the authorship policy in `approval.md`.
- Paraphrasing in DOCX: export with `"$REPORT_PYTHON" "$REPORT_AUTOMATION_ROOT/tools/draft_docx.py" export <folder>`, import the user's edits with `... import <folder> <docx>` (show the diff, add `--apply` only on their confirmation), and never regenerate a draft that is open in an editor (the tool refuses while a lock file exists).
